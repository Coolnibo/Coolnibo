#### 分布式计算与性能调优专场（核心深挖）

> **面试官提问**： “你在南网项目中提到，主导了 PowerJob 调度方案设计，并搭建了 Flink 集群来解决全省大规模电量电费试算的计算瓶颈。 请具体讲讲：在处理全省海量用户初始化和多月试算时，你遇到的**最头疼的一个性能瓶颈（慢 SQL 或数据倾斜）**是什么？你是通过什么步骤去排查和彻底解决的？Flink 的并行度和窗口函数在这里是怎么调优的？”


在处理全省海量用户初始化和多月电量电费试算时，我遇到的最大挑战其实是**数据库层面的连接雪崩与计算层面的性能瓶颈**。具体我是通过以下几个步骤排查并彻底解决的：

**第一步：定位与排查（破案过程）** 
当时全省数据并发跑批时，系统频繁报错，甚至导致 PostgreSQL 数据库直接崩溃重启。我们通过查看 Linux 系统日志、PostgreSQL 的 `pg_stat_activity` 活跃会话以及 Flink 任务端的异常栈，发现根本原因是：入库算子触发了大量并发任务，每个任务都在短时间内向 PG 数据库建立大量长/短连接，瞬间打满了 PG 的 `max_connections`，导致数据库内存和连接数耗尽而触发 OOM 或重启。

**第二步：组合拳解决连接与分布式瓶颈**

1. **连接池治理**：我们在架构中引入了 **PgBouncer** 中间件，采用事务级连接池管理，把flink入库算子成千上万的直连请求复用到后端有限的数据库连接上，彻底解决了连接数被打满的问题。同时配合数据库分库和读写库规划，分散读写压力。
    
2. **Flink 算子与并行度调优**：在计算端，起初我们是静态指定并行度。后来针对全省数据量不均导致的数据倾斜问题，我们在 Flink Web UI 中通过观察各个 TaskManager 的 **Backpressure（背压）** 和 **Busy 状态**，精准定位到了堵塞的算子。
    
3. **窗口与计算逻辑优化**：我们优化了窗口函数的触发逻辑，并合并了部分不必要的算子（减少线程间切换开销），结合 SQL 的深度慢 SQL 治理。
    

**最终结果**：经过这套组合拳改造后，整个试算系统不仅扛住了全省海量数据的并发冲击，而且成功从最初的‘单区域跑不动’，平稳升级支持了全省三个月数据的批量自动化高效执行。”


#### 2. 数据库与国产化适配专场

> **面试官提问**： “简历里看到你接触了 PostgreSQL、MySQL 以及达梦（DM）等国产数据库。在大规模电量电费计算中，单点向集群架构升级时，你们是如何做分库规划和读写库策略的？达梦和 PostgreSQL 在实际开发中有哪些让人头疼的‘坑’（比如兼容性或语法差异）你是怎么避开的？”

**面试官，关于单点向集群升级、分库规划以及达梦与 PG 的适配，我们在实际项目中是踩过很多真坑、做了不少底层硬核工作的：**

**1. 分库规划与读写策略（读写异构与架构解耦）** 在全省试算场景下，我们采用了**读写异构**的架构设计：

- **读链路**：我负责的用户初始化模块，主要针对营销主系统历史旧库进行**只读操作**。为了保护生产主库，我们通过优化 Slow SQL，将计算关系拉取后绑定发送到 Kafka 消息队列，实现读写解耦。
    
- **写链路**：Flink 计算后的海量试算结果数据，通过批量写入直接落入我们**单独规划的试算结果集群**，并基于地区（如州市维度）和时间维度做了分库分表，分散写入与存储压力。
    

**2. 达梦（DM）与 PG 的适配“血泪坑”与底层重构（核心亮点）** 在从 PG 迁移/适配达梦数据库的过程中，由于国产数据库与 PG 在 SQL 解析、函数支持和字符处理上存在不少差异，我们没有仅仅依赖第三方中间件，而是**深入持久层框架做了很多定制化适配工作**：

- **重写 SQL Dialect（方言适配）**： 我们在 ORM / 持久层（如 Hibernate/MyBatis/ShardingSphere 扩展点）中**自定义并重写了 SQL Dialect**。重构了分页逻辑（处理 `LIMIT/OFFSET` 与达梦 `ROWNUM/TOP` 的差异）、序列生成策略机制，以及部分复杂方言 SQL 的解析逻辑。
    
- **数据库函数映射与配对（Function Mapping）**： PG 和达梦在字符串处理、日期格式化（如 `TO_CHAR`、`DATE_TRUNC`）以及 JSON 节点提取函数上名称和入参不一致。我们在 Dialect 里做了一整套**自定义函数注册与映射配对**，让上层业务代码无需关心底层到底是 PG 还是达梦，由 Dialect 自动转换成对应数据库的内置函数。
    
- **字符转义与大小写/特殊字符治理**： 达梦在处理某些转义字符（如 `\`、`'`）、特殊符号以及默认大小写敏感度上与 PG 存在差异，容易引发 SQL 语法报错或注入风险。我们针对达梦的解析特性，在持久层拦截器和 SQL 构建工具中**重写了字符转义与参数绑定逻辑**，彻底解决了跨库兼容性问题。
    


#### 3. AI 应用与工程化落地专场

> **面试官提问**： “你用 Ollama 部署了 Qwen3、DeepSeek，并结合 Spring AI 和 LangChain4j 做了业务集成。 很好奇在实际落地中，本地大模型面临的主要痛点是什么（比如显存占用、并发推理延迟、长文本上下文限制）？你的业务系统具体调用大模型做了什么功能？有没有做过 RAG（检索增强生成），如果做过，PostgreSQL 的向量检索性能表现如何？”

 **面试官，我们在本地大模型部署和业务落地过程中，遇到最大的挑战是：由于服务器没有配置 GPU，纯靠 CPU 推理大模型，响应延迟较高。为了解决用户端漫长等待的体验痛点，我们设计了一套【Spring WebFlux + EventSource（SSE）+ Nginx】的异步流式传输架构：**
  **1. 纯 CPU 环境下的模型工程化（量化与部署）**
> 
> - 我们采用 GGUF 格式的量化模型（如 Q4_K_M），配合 Ollama 的 `Modelfile` 固化系统提示词和上下文。
>     
> - 在后端 Java 层，所有的电量电费硬核计算（如同比、环比、总金额）全部由后端精确算好，大模型只负责接收结构化数据并生成自然语言的用电提示，从源头上杜绝了模型幻觉和算术错误。
>     
> 
> **2. 核心架构亮点：WebFlux + SSE + Nginx 异步流式输出（重点）** 针对 CPU 推理较慢、单次请求耗时长的痛点，我们彻底抛弃了传统的同步 HTTP 阻塞接口：
> 
> - **后端响应式链路（Spring WebFlux）**：我们在 Spring AI / LangChain4j 的集成层中，利用 **`Flux<String>`（响应式数据流）** 将大模型分片吐出的文本封装成异步数据流。每生成一个 Token，就通过 Reactive 管道向下游推送。
>     
> - **前端实时渲染（EventSource / SSE）**：前端采用原生的 **`EventSource`** API 建立长连接，完美适配浏览器的 SSE 协议，实现了类似 ChatGPT 的**流式“打字机”效果**。用户不需要死等整个大模型推理结束，只要第一个 Token 出来就能实时看到结果，体验极佳。
>     
> - **中间件代理优化（Nginx）**：在 Nginx 代理层，我们针对流式传输做了专项调优。关闭了代理缓冲（`proxy_buffering off;`），禁用了响应缓存，并设置了合适的超时时间（`proxy_read_timeout`），确保大模型的文本流能够穿透 Nginx 实时、无延迟地推送到前端客户端。
>     
> 
> **3. 关于向量化检索的技术储备**
> 
> - 虽然后续业务中暂时没有硬性接入 RAG，但我对 **PostgreSQL + pgvector** 向量数据库做过深度的技术调研。利用现有的 PG 关系型数据库扩展，未来可以低成本地实现海量电价文档和电力政策的向量化检索，作为智能化用电咨询的演进方向。”
